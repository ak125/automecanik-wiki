# Quality Gates

> Conditions obligatoires avant promotion d'une fiche `proposals/` → `wiki/`,
> et avant export `wiki/` → `exports/`.
>
> Schema canonique : `_meta/schema/frontmatter.schema.json` (v1.0.0).
> Plan canon : [ADR-031](../../governance-vault/ledger/decisions/adr/ADR-031-four-layer-content-architecture.md) §D14-D23, plan rev 6 (verifier-dans-existant).

______________________________________________________________________

## §1 — Validation automatique par preuves

La décision est automatique : les contrôles satisfaits permettent la promotion, les contrôles échoués ou indisponibles la bloquent. Aucune étape de validation humaine n'est obligatoire pour une fiche WIKI. Les cas bloqués doivent obtenir les preuves manquantes ou être corrigés puis réévalués.

La politique opérationnelle est définie au §7. Les scores et heuristiques ci-dessous sont des contrôles nécessaires, pas une preuve suffisante à eux seuls. Les transitions vers les applications consommatrices restent régies par leurs propres contrats.

______________________________________________________________________

## §2 — Gates automatiques (lecture seule, aucune écriture DB)

Sur chaque fiche `proposals/<slug>.md`, le pipeline `_scripts/quality-gates.py` vérifie :

| #   | Contrôle                             | Méthode                                                                                 | Verdict     |
| --- | ------------------------------------ | --------------------------------------------------------------------------------------- | ----------- |
| 1   | Frontmatter valide                   | Schema v1.0 (`_meta/schema/frontmatter.schema.json`, JSON Schema 2020-12)               | PASS / FAIL |
| 2   | Sources présentes                    | `source_refs ≥ 1` (sauf `truth_level: L4`)                                              | PASS / FAIL |
| 3   | Sources résolvables                  | Fichier `automecanik-raw/<path>` existe ou URL accessible                               | PASS / WARN |
| 4   | Sections obligatoires                | Cf. template `_meta/templates/<entity_type>.md`                                         | PASS / FAIL |
| 5   | Slug unique                          | Comparaison `_meta/entity-registry.json`                                                | PASS / FAIL |
| 6   | Pas de pollution scrape              | Skill `pollution-scanner` mode lint read-only (Textar, Brembo, "Skip to main content"…) | PASS / WARN |
| 7   | Pas de mélange catalogue             | Heuristique : prix, stock, SKU, compatibilité exacte produit/véhicule                   | PASS / FAIL |
| 8   | Liens internes valides               | Résolution dans `wiki/`                                                                 | PASS / WARN |
| 9   | Anti-duplication                     | Comparaison fingerprint vs fiches existantes                                            | PASS / WARN |
| 10  | Cohérence avec raw                   | `source_refs` pointent vers `automecanik-raw/sources/` ou `recycled/`                   | PASS / WARN |
| 11  | Pas de promesse commerciale          | Heuristique : « meilleur », « garanti », « le moins cher »…                             | PASS / FAIL |
| 12  | Pas d'affirmation safety non sourcée | Mots-clés safety + source `confidence: high` requis                                     | PASS / FAIL |
| 13  | `confidence_score` ≥ seuil           | Formule §4 calculée par `_scripts/compute-confidence-score.py`                          | PASS / WARN |

Les rapports vivent dans `_meta/qa-reports/<date>/`. **Artefacts d'audit ; ne remplacent pas les fiches ni les manifests raw.**

## §3 — Classification du risque (`risk_level`)

| Niveau       | Exemples                                                                                                | Action par défaut                                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| **low**      | glossaire, synonymes, descriptions générales, KW non critiques                                          | auto-promotion possible                                                                                                     |
| **medium**   | gammes, constructeurs, vehicles généraux, FAQ non contractuelle                                         | auto-promotion possible si score §4 ≥ 0.85 + sampling périodique                                                            |
| **high**     | diagnostic freinage/direction/batterie, conseil pouvant influencer une réparation, support sensible     | promotion possible **uniquement** si sources solides ET mentions de prudence présentes ; sinon `in_review`. Export `false`. |
| **critical** | paiement, retour, garantie, livraison contractuelle, compatibilité exacte, prix, stock, sécurité légale | blocage automatique si preuve insuffisante                                                                                  |

## §4 — Formule `confidence_score` (déterministe)

```
confidence_score =
    0.40 × moyenne(source_refs[].confidence_numeric)   # high=1.0, medium=0.6, low=0.3
  + 0.30 × (sections_remplies / sections_obligatoires)
  + 0.20 × (links_internes_resolus / max(links_internes_total, 1))
  + 0.10 × (1.0 si ≥ 2 source_refs avec types distincts sinon 0.0)
```

- Calculée par `_scripts/compute-confidence-score.py`
- **Mode `--check`** (par défaut au pre-commit) : vérifie que la valeur écrite est cohérente avec la formule. FAIL si l'auteur a triché.
- **Mode `--fix`** explicite : l'auteur lance le script pour réécrire le score. Pas de magie automatique au commit.
- Idempotent : recalcul sur même contenu = même score.
- Seuils par `risk_level` : low ≥ 0.70, medium ≥ 0.85, high ≥ 0.95.

## §5 — `blocked_reasons` (vocabulaire fermé)

Valeurs autorisées dans `blocked_reasons[]` :

```
schema_invalid             — frontmatter ou template invalide
sources_missing            — source_refs vide
sources_unresolvable       — au moins 1 source_ref ne résout pas
sections_missing           — sections obligatoires manquantes
slug_collision             — slug déjà présent dans entity-registry
pollution_detected         — pollution scrape (Textar, Brembo, fragments HTML)
catalog_leak               — prix/stock/SKU/compatibilité exacte détectés
commercial_promise         — promesse commerciale détectée
safety_unsourced           — affirmation sécurité critique sans source haute confiance
duplication_detected       — fiche fingerprint très proche d'une fiche existante
source_conflict            — sources contradictoires
confidence_below_threshold — score < seuil pour le risk_level
post_hoc_source_disproven  — source devenue fausse après promotion (rollback §7)
human_review_pending       — ancien code conservé pour historique, non émis comme attente obligatoire

# Gates ADR-033 §D1-§D3 (canon diagnostic_relations[])
relation_to_part_missing   — entrée diagnostic_relations[] sans relation_to_part
symptom_unstructured       — symptôme implicite dans le corps non miroité dans diagnostic_relations[]
confidence_overclaimed     — evidence.confidence: high mais source_type ne le permet pas (cf. source-policy.md §9.1)
source_policy_violated     — source_policy: 1_high mais aucune source confidence: high ;
                             ou source_policy: 2_medium_concordant mais < 2 sources medium concordantes
legacy_symptoms_block      — présence de diagnostic.symptoms: (bloc legacy interdit ADR-033 §D2)
forbidden_systemes_dir     — fichier dans wiki/systemes/ (anti-pattern ADR-033 §D3)
forbidden_per_symptom_file — fichier wiki/diagnostic/<symptom>-*.md matchant pattern interdit (ADR-033 §D3) ;
                             le dossier wiki/diagnostic/ lui-même reste autorisé (ADR-032 §D1)
source_slug_unknown        — slug cité dans diagnostic_relations[].sources[] absent de _meta/source-catalog.yaml
maintenance_advice_missing — fiche gamme matchant un kg_nodes.MaintenanceInterval
                             mais sans entity_data.maintenance.educational_advice (ADR-032 §D1)
```

Tout autre valeur fait échouer le gate `schema_invalid`.

## §5.bis — Gates spécifiques ADR-033 (canon `diagnostic_relations[]`)

### Validation granulaire par symptôme (ADR-033 §D1, source_policy)

Pour **chaque** entrée `diagnostic_relations[]` :

| `source_policy`       | Règle                                                                                                            |
| --------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `1_high`              | ≥ 1 source `confidence: high` ET son `source_type` autorise `high` (cf. `source-policy.md §9.1`)                 |
| `2_medium_concordant` | ≥ 2 sources `confidence: medium`, citant des **références distinctes** (pas simplement deux pages d'un même PDF) |
| `manual_review`       | Fiche bloquée → `status: in_review` jusqu’à vérification automatique des preuves                                 |

Sinon → `blocked_reasons: [source_policy_violated]`.

### Détection des symptômes implicites (gate `symptom_unstructured`)

Si le corps de la fiche contient un lexique de symptôme français (« bruit », « grincement », « vibration », « voyant », « fumée », « surchauffe », « fuite », « jeu », « broute », « claquement », « sifflement », « usure anormale ») **et** qu'aucune entrée `diagnostic_relations[]` ne couvre ce symptôme → `blocked_reasons: [symptom_unstructured]`.

Le rédacteur doit soit retirer la mention textuelle, soit ajouter une entrée structurée correspondante.

### Anti-patterns ADR-033 §D3

| Anti-pattern                                                                                                                                                             | Gate                         |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------- |
| Fichier sous `wiki/systemes/`                                                                                                                                            | `forbidden_systemes_dir`     |
| Fichier `wiki/diagnostic/<symptom>-*.md` matchant regex `(bruit\|grincement\|vibration\|voyant\|fumee\|surchauffe\|fuite\|usure\|symptome\|claquement\|sifflement)-*.md` | `forbidden_per_symptom_file` |
| `diagnostic.symptoms:` dans frontmatter (legacy)                                                                                                                         | `legacy_symptoms_block`      |

> **Note** : Le dossier `wiki/diagnostic/` lui-même reste **autorisé** pour fiches macro-pédagogiques (vocab UI, FAQ, signes diagnostic) per ADR-032 §D1.

### `evidence.diagnostic_safe` (séparation preuve SEO vs preuve diagnostic-live)

| `diagnostic_safe`            | Conséquence                                                                                                                              |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `false` (défaut ADR-033 §D4) | La relation peut enrichir la fiche wiki (SEO/contenu), mais **n'est pas autorisée à influencer le moteur diagnostic LIVE** (`__diag_*`). |
| `true`                       | Autorisé à alimenter le moteur diagnostic. **Flip humain ciblé uniquement** (commit signé reviewer ≠ auteur, cf. ADR-033 critère §9).    |

Le défaut conservateur est non-négociable : pas de flip automatique en bulk possible.

## §6 — Réévaluation continue

Les propositions bloquées sont réévaluées après correction des causes, avec les mêmes contrôles. Une revue humaine peut contribuer des informations, mais n'est ni un passage obligatoire ni un moyen de contourner une preuve manquante.

## §7 — Validation et promotion automatiques

Décision utilisateur du 12 septembre 2026 : supprimer la validation humaine systématique. Le décideur existant `_scripts/promotion_decision.py` compose substance, qualité, couverture, régression et provenance ; `promote.py` est son interface. Il n'existe pas de second décideur LLM.

Conditions cumulatives pour le moteur legacy actuellement sélectionné :

- cinq contrôles source/claim/contradiction/risk/confidence PASS ;
- score déterministe au moins 0.85, niveaux L1/L2 et deux types de sources distincts ;
- couverture stricte et provenance vérifiables, aucune régression bloquante ;
- aucune condition de sécurité ou valeur critique que le moteur ne sait pas vérifier ;
- aucune relecture ni autorité diagnostic déclarée par la proposition elle-même (`evidence.reviewed`, `evidence.diagnostic_safe`, `diagnostic_not_applicable.reviewed` autres que false, ou clé `evidence.reviewed_by` / `evidence.reviewed_at` présente, quelle que soit sa valeur), quelle que soit la famille : motif `REVIEW_AUTHORITY_CLAIMED`. La correction attendue est de remettre ces valeurs à false et de retirer le cachet. Leur bascule à true reste humaine ou couverte par une règle d'ADR explicite (ADR-033 D4, §5.bis ; pour `reviewed` des relations hors sécurité, ADR-116, ci-dessous) ;
- empreintes des entrées et des moteurs identiques entre décision et écriture.

Le seuil 0.85 conserve le plancher de qualité déjà documenté. Ce n'est ni une probabilité de vérité ni une calibration statistique démontrée. L'ancien défaut 1.01 désactivait toutes les promotions ; il est remplacé par 0.85. Le CLI permet seulement de renforcer ce seuil jusqu'à 1.0. Le moteur six dimensions reste un chantier distinct, sans bascule implicite.

Résultats : `ELIGIBLE` autorise l'exécuteur ; `BLOCKED` et `UNKNOWN_FAIL_CLOSED` maintiennent la proposition avec des motifs structurés. Correction des preuves puis nouvelle évaluation automatique. Aucun échec ne crée une attente humaine obligatoire. Les identifiants historiques tels que `SAFETY_HUMAN_REVIEW` restent compatibles avec les consommateurs existants ; leur résultat est un blocage technique, pas une tâche humaine.

Un catalogue de l'arbre des scripts absent ou illisible, ou dont `source_type_max_confidence` ou `source_type_editorial_role` est manquant, invalide ou sans parité de clés, arrête l'exécution avant tout calcul (code 2, aucune décision écrite), au chargement de `quality-gates.py` ; dans l'exécution habituelle, ce catalogue est celui de l'arbre évalué. Une entrée gouvernée absente de l'arbre évalué rend fausse la condition qui la lit, avec `status: UNAVAILABLE` et la liste `unavailable_conditions` : un défaut d'infrastructure, jamais un verdict sur le contenu. C'est le cas de `_meta/numeric-plausibility.yaml` (`numeric_exactitude_verified`) et, quand l'arbre évalué est distinct de celui des scripts (revue `gap1`), de `_meta/source-catalog.yaml` (`proof_sources_min`, et l'export diagnostic que lit `numeric_exactitude_verified`, sauf violation prouvée ailleurs) ; une couverture, une régression ou une provenance absente garde son motif `*_GATE_UNAVAILABLE`. Seule une plage `validated` de `_meta/numeric-plausibility.yaml`, corroborée par deux sources captées distinctes, rend une valeur dimensionnée vérifiable : tant que les plages restent `proposed`, toute fiche sécurité portant une valeur avec unité reste bloquée. Seul le corps porte des ancres : une valeur dimensionnée du frontmatter ou d'un export n'est jamais vérifiable, même sur une plage `validated`, et bloque la fiche. Une telle valeur se publie donc dans la prose ancrée du corps, que l'export SEO ne reprend pas.

`numeric_exactitude_verified` lit le texte publié sans connaître ses lecteurs : la fiche du canon est publique et un lecteur peut en servir n'importe quel champ, donc aucune liste de champs ne borne la lecture. Elle est prudente : une chaîne interne (`review_notes`, slug, URL, suite d'échappements `%XX`) qui porte un nombre suivi d'une unité ou de `%` (`Manuel_2019_%28FR%29.pdf`, lu sans balisage, compte `2019%`), ou un nombre nu dans une clause qui nomme une grandeur dimensionnée de la famille, compte comme une valeur affichée et la fiche reste bloquée, comme aujourd'hui toute fiche sécurité. Le monde fermé a le même coût : bloquent aussi une note de bas de page, note en ligne d'Obsidian comprise, fermée ou non (`[^n` sans `]`), toute insertion `![[…]]` et tout lien `[[…|…]]`, `[[…#…]]` ou `[[…^…]]` d'Obsidian, tout lien `[[….md]]`, tout `%%`, tout dernier mot de ligne qui porte un `^` suivi d'un caractère (`10^3`), hors note, tout bloc `query` ou `base`, toute citation dont la première ligne commence par `[!` (`> [!note]`), quel que soit le bloc qu'elle ouvre, tout HTML brut (dans une chaîne publiée, un lien automatique `<https://…>` et une balise écrite en code compris), tout `$`, prix compris, tout caractère d'une écriture de droite à gauche (hébreu, arabe), tout nom entre deux deux-points hors heure (`:100:` d'un rapport `1:100:5`), tout chiffre non décimal (chiffre romain `Ⅻ`, idéogramme `三`), toute fraction (`½`, `1⁄2`), toute image, tout caractère que la base Unicode de l'interpréteur ne définit pas (dont ceux d'une version d'Unicode plus récente), toute chaîne publiée qui commence par une unité, ou par un mot qui en commence une (`barre de torsion`, lu `bar` ; `Inchangé`, lu `Inch`), tout item de liste ordonnée qui commence, après une case à cocher éventuelle (`[x]`), par un chiffre, une unité, un mot qui en commence une (`1. Inchangé`, lu `1. Inch`) ou un bloc vide, invisible ou blanc et, dans un corps dont un décodage diffère du texte écrit (échappement `%XX`, entité), une balise ou un `$` écrit en code. La lecture squelette sur-approxime de même : elle joint ce que sépare un signe qu'elle retire (`20-30%` y compte `2030%`), extrait ancré compris (`10-20 Nm` y est classé `1020 Nm`, hors plage). Résidus, non détectés :

- un nombre sans unité adjacente : écrit seul dans un champ (nombre YAML ou JSON, ou chaîne) dont l'unité est dans sa clé ou dans un champ voisin qui ne commence pas par elle, ou, en fin de champ, suivi d'une partie de son unité dont le champ voisin porte le reste (`25 N` puis `m`, que les surfaces R3 joignent en `25 Nm`) ; dans le corps, séparé de son unité par du texte ou de la structure (unité avant le nombre, en en-tête de colonne, en amorce de liste, après deux-points) ; nu, dans une clause dont la grandeur n'a pas de plage pour la famille de la fiche dans `_meta/numeric-plausibility.yaml` ;
- une unité ou un chiffre écrit en lettres qui leur ressemblent (`Νm`, nu grec ; `2Ƽ Nm`, lettre latine ton cinq ; `2З`, zé cyrillique ; `O` pour `0`) ; un chiffre décimal d'une autre écriture (bengali, dévanagari), lu à sa valeur quel que soit le chiffre latin auquel son glyphe ressemble ; un caractère visible que la lecture squelette retire (marque combinante, guillemet, symbole d'espace `␣` ou `〿`), entre un nombre et son unité ou entre deux de ses chiffres, est, lui, lu, extrait ancré compris ;
- un caractère que la lecture squelette garde entre un nombre et son unité : ponctuation de nombre ou de clause (`20.Nm`, `20,Nm`, `20; Nm`, `20: Nm`, ou un chiffre de compatibilité qui l'écrit, `⒛` pour `20.`), point médian ou signe degré qui n'écrit pas une unité (`N·m`, `°C`) : `20·Nm`, `20 · Nm`, `20°Nm`. La lecture squelette le garde et `numeric_exactitude.py` n'y lit aucune valeur ; seul un nombre nu dans une clause qui nomme une grandeur dimensionnée de la famille y est compté ;
- une valeur écrite en pictogramme (`🔟`, `💯`), sans valeur numérique Unicode, ou en mots (`vingt-cinq Nm`, `XXV Nm` en lettres latines) : `numeric_exactitude.py` ne lit que les chiffres décimaux ;
- une unité prolongée par un caractère (`25 mm2`) : `numeric_exactitude.py` lit l'unité sans borne à droite, la valeur reste comptée, sous l'unité qu'elle prolonge (`25 mm`) ;
- un nombre dont les groupes de chiffres sont séparés par un séparateur de milliers (espace, insécable ou fine : `1 200 Nm`), par une barre oblique (fraction : `1/2 Nm`) ou par tout caractère visible que la lecture squelette garde ou change en espace (lettre, lettre modificative comprise : `1ʼ200 Nm`, `1ʹ200 Nm` ; point médian, ou ce que la compatibilité y ramène : `1·200 Nm`, `1·5 Nm` écrit pour `1,5 Nm` ; signe `×` entre deux nombres : `2×25 Nm` ; point en chef, changé en espace : `1˙200 Nm`) : `numeric_exactitude.py` n'en lit que le dernier groupe (`200 Nm`, `2 Nm`, `5 Nm`, `25 Nm`) ; un extrait ancré qui le porte est classé sur ce groupe, plage et concordance des sources comprises (`1 200 Nm` d'une source y corrobore `200 Nm` d'une autre), et, pour une barre oblique, aussi sur les chiffres joints de sa lecture squelette (`12 Nm`) ;
- une valeur dont les chiffres sont ceux d'une suite d'échappements d'un caractère non ASCII (`%E2%80%89 bar`) : la lecture la décode, comme une URL accentuée (`%C3%A9`) qu'elle ne compte pas comme `3%`, mais hors d'un lien la page l'affiche telle qu'écrite, ses derniers chiffres devant l'unité (`89 bar`) ;
- le contexte d'un extrait ancré : il est classé sur son propre texte, sa phrase hors de l'ancre n'entre pas dans sa clause ;
- les valeurs que seule l'application connaît (SHA du commit, horodatages) : lues sur des valeurs neutres de la forme que la promotion écrit (SHA court de repli, horodatage ISO-8601) ;
- le texte du catalogue de sources que `exports/diagnostic/` reprend : lu tel qu'il est à la décision, pas tel que le régénère une modification ultérieure du catalogue ;
- deux graphies d'un même éditeur : `publisher` est un texte libre du catalogue ; casse, espaces, forme Unicode et caractères invisibles sont normalisés, une autre orthographe compte pour un autre éditeur.

Même toutes conditions prouvées, la fiche reste bloquée tant que la constante de code `SAFETY_AUTO_APPROVAL_ADR` (`promotion_decision.py`) est vide : le motif `SAFETY_HUMAN_REVIEW` porte alors `policy.status: not_ratified`. Elle ne se lève ni par variable d'environnement ni par option CLI, mais par une PR WIKI dédiée qui y inscrit l'ADR vault acceptée amendant ADR-091 §4 et ADR-093. Le fichier entre dans l'empreinte du moteur de décision : changer la constante invalide toute décision déjà rendue. Levée par ADR-114 (acceptée le 2026-10-15), la constante a été remise à vide le 2026-10-22 (ADR-114 §Retour arrière) : la gate est refermée.

`gap1_auto_review.py` reporte cette décision et y ajoute ses conditions sur les claims RAW extraits (pages captées, sources candidates, valeurs chiffrées, `raw_ref` du catalogue) ; il ne décide rien seul. Les entrées gouvernées absentes de son répertoire de travail (`_meta/source-catalog.yaml`, `_meta/numeric-plausibility.yaml`, que la revue n'y copie pas) y rendent `proof_sources_min` et `numeric_exactitude_verified` `UNAVAILABLE` : elles sont rapportées à part, « non évaluables dans ce contexte », et restent bloquantes ; son propre contrôle chiffré des claims RAW lit les plages du dépôt. Résidus V2 : détection de contradiction dans la prose (aujourd'hui déclarative), validation des plages chiffrées, ancrage d'une valeur du frontmatter ou d'un export à sa source.

### Relecture des relations hors sécurité par la règle de preuve (ADR-116)

Pour chaque entrée `diagnostic_relations[]` d'une fiche hors sécurité (pas `is_safety_proposal` ; un doute vaut sécurité), le décideur calcule les conditions d'ADR-116 D2. Il les calcule dans `evaluate_tier` (`relation_review`) et les compose dans la décision (`relation_review.relations[]`). Une relation est relue par la règle si toutes sont prouvées :

- `fiche_eligible` : la fiche qui la porte est `ELIGIBLE` ;
- `not_safety` : la fiche n'est pas une proposition de sécurité ;
- `sources_raw_proven` : chaque source de la relation est `raw_proven` au sens de l'export diagnostic (`active` avec `raw_ref`) ;
- `citations_anchored` : au moins une citation, toutes valides (`_citation_issues`) et ancrées dans l'archive RAW épinglée (`gate_citation_anchors`) ;
- `proof_publishers_min` : au moins 3 éditeurs distincts de rôle `proof` parmi les sources des citations ancrées, comptés comme `proof_sources_min` de la Safety Auto-Gate ;
- `source_policy_resolved` : `source_policy` posée et différente de `manual_review`, aucun `source_policy_violated` ni `schema_invalid` sur l'entrée ;
- `numeric_verified` : le texte publié de la relation (fiche et export diagnostic) a au moins une chaîne lue et aucune violation chiffrée (`numeric_exactitude_verified`, attribuée par relation) ;
- `no_review_claimed` : aucun motif `REVIEW_AUTHORITY_CLAIMED`.

Une condition dont le calcul échoue est fausse et son erreur est rapportée. Une entrée gouvernée absente (catalogue, inventaire RAW) la rend fausse et `UNAVAILABLE`. Une relation non relue ne bloque jamais la fiche : aucune de ces conditions n'est un motif de blocage. La trace de chaque relation porte ses conditions, `blocking_conditions`, les éditeurs comptés et non comptés avec leur raison, et `policy.status` (`ratified` ou `not_ratified`).

L'écriture est gardée par la constante de code `RELATION_REVIEW_ADR` (`promotion_decision.py`). Tant qu'elle est vide, le décideur est en report-only : il inscrit `would_review` dans sa trace et n'écrit rien dans la fiche. Une fois levée, seul `apply_promotion` écrit. Pour une relation prouvée, il écrit `reviewed: true`, `reviewed_by: rule:ADR-116@<révision du décideur>` et `reviewed_at` (UTC). Pour toute autre relation hors sécurité, il écrit `reviewed: false` sans cachet. La relecture n'est jamais héritée : la proposition porte `reviewed: false`, et la relecture est recalculée à chaque promotion. La constante ne se lève ni par variable d'environnement ni par option CLI, mais par une PR WIKI dédiée, recevable une fois les préconditions d'ADR-116 D4 fusionnées. Le fichier entre dans l'empreinte du moteur de décision. `diagnostic_safe` reste un flip humain ciblé (§5.bis).

Une ancre ne casse pas en silence. `quality-gates.py --cross-repo` vérifie les ancres des citations de toutes les fiches du canon. `check-activation-guard.py` traite le changement du `raw_ref` d'une source déjà `active` comme une activation, soumise au flux gouverné qui exécute `--cross-repo`.

La validation du WIKI n'autorise aucune modification du moteur diagnostic LIVE.

```bash
python3 _scripts/promote.py --wiki-root /chemin/wiki --raw-root /chemin/raw --all --dry-run
python3 _scripts/promote.py --wiki-root /chemin/wiki --raw-root /chemin/raw --target proposals/fiche.md --apply
```

`--apply` déclenche l'exécuteur, pas une revue humaine. Le dry-run permet de diagnostiquer sans écrire. L'activation d'un appelant périodique reste distincte de cette politique de décision.

## §9 — Quarantine `status: quarantined` (frontmatter, pas de move Git)

> **Distinction stricte** :
>
> | Mécanisme                           | Niveau | Contenu               | Localisation physique            |
> | ----------------------------------- | ------ | --------------------- | -------------------------------- |
> | `automecanik-raw/quarantine/`       | RAW    | source brute douteuse | dossier dédié                    |
> | `status: quarantined` (frontmatter) | WIKI   | proposal douteuse     | reste dans `proposals/<slug>.md` |

Une proposal qui échoue gravement reste dans `proposals/<slug>.md` avec `status: quarantined`. Pas de déplacement physique.

```yaml
status: quarantined
review_status: in_review
validation_mode: automatic
blocked_reasons: [pollution_detected, source_conflict]
quarantined_at: 2026-04-29T14:23:00Z
```

Avantages : historique Git linéaire, recovery `quarantined → in_review` après correction, compat sampling §6.

## §10 — Rollback (rétrogradation in-place + audit log JSONL)

Si une fiche promue dans `wiki/<entity_type>/` est ensuite identifiée problématique :

1. **Rétrogradation in-place** (pas de `git revert` — préserve la généalogie) :
   ```yaml
   status: in_review
   review_status: in_review
   blocked_reasons: [post_hoc_source_disproven]
   rollback_from_commit: <sha>
   rollback_reason: <free_text_short>
   rollback_at: 2026-04-29T14:23:00Z
   ```
1. **Move Git** : `wiki/<entity_type>/<slug>.md` → `proposals/<slug>.md` (commit *rollback*)
1. **Audit log append-only** dans `_meta/audit-log.jsonl` :
   ```json
   {"ts":"2026-04-29T14:23:00Z","action":"rollback","slug":"plaquette-de-frein","entity_type":"gamme","from_status":"auto_reviewed","to_status":"in_review","commit":"<sha>","reason":"source_disproven","actor":"<handle>"}
   ```
1. **CI re-run** : `wiki-quality-gates.yml` ré-évalue depuis `proposals/`.

Idempotent et traçable sans réécrire l'histoire Git.
